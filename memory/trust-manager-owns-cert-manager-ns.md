`infra/trust-manager/requirements.yaml` declares `Namespace/cert-manager` (the `${TRUST_MANAGER_NAMESPACE:-cert-manager}` namespace). Any Flux `Kustomization` with `prune: true` whose path is `./infra/trust-manager` therefore **adopts** `Namespace/cert-manager` into its inventory. Deleting that Kustomization prunes the namespace, which cascades: cert-manager, trust-manager, and every secret in that namespace (`vault-pki-ca`, `vault-pki-token`, `cluster-ca-secret`) get deleted.

**Why:** On the platform-sthings cluster (labul/vsphere), spinning up a *throwaway test* Kustomization at `./infra/trust-manager` and later deleting it tore down the real cert-manager. The cluster also accumulated Rancher debris that blocked recovery: a `rancher.cattle.io` Validating/MutatingWebhookConfiguration and a stale `v1.ext.cattle.io` APIService (ServiceNotFound) — both fail *closed* and block namespace deletion/creation cluster-wide until removed.

**How to apply:** Never point a disposable test Kustomization at `./infra/trust-manager` (or any base that declares a shared namespace) with `prune: true`. To test infra changes, suspend the prod Kustomization and reuse it, or test in an isolated namespace. `vault-pki-ca` / `vault-pki-token` are **Terraform-owned** (`vault-cert-issuer/vault.tf` + the `vault-base-setup` module), NOT flux-managed, so they do not self-heal — `vault-pki-ca`'s `ca.crt` equals `base64 -d` of the `vault-pki` ClusterIssuer's `spec.vault.caBundle`, but `vault-pki-token` can only be reminted by `terraform apply`.

**vault-cert-issuer apply gotcha (resolved 2026-06-01):** `vault_ca_bundle` (variable in `vault-cert-issuer/variables.tf`, default `""`) is NOT in `terraform.tfvars.sops.json` — it must be exported as an env var before `terraform apply`, per the README Usage section: `export TF_VAR_vault_ca_bundle=$(curl -sk "$VAULT_ADDR/v1/pki/ca/pem" | base64 -w0)`. If you forget it, the apply writes a ClusterIssuer with an empty/unreadable `caBundle` (→ vault-pki fails TLS `x509: certificate signed by unknown authority`) AND a `vault-pki-ca` secret with empty `ca.crt` (→ trust bundle silently missing the Vault PKI CA). The Vault PKI CA == Vault's serving-cert CA here (`CN=infra.sthings-vsphere.labul.sva.de`). Correct apply env: `VAULT_ADDR`, `VAULT_SKIP_VERIFY=true`, `VAULT_TOKEN` (from `vault-root-token` secret in `vault` ns on the **infra-sthings** kubeconfig), plus the `TF_VAR_vault_ca_bundle` export. The tfvars `.sops.json` keys are UPPERCASE Vault env vars, not TF vars, and are not auto-loaded. A fresh apply also remints `vault-pki-token`, which fixed a long-standing cert-signing `403`. **Durable fix in place:** `platform-sthings/vault-cert-issuer/Taskfile.yaml` (`task plan|apply|verify`) now fetches the live CA and sets all env automatically — use it instead of bare `terraform apply`.

Also note: deploying Rancher *Server* (even briefly) installs Fleet + Turtles + CAPI — ~94 `*.cattle.io`/`cluster.x-k8s.io` CRDs, ~13 `cattle-*`/`fleet-*`/`local`/`p-*` namespaces, cattle ClusterRoles/Bindings (some with `wrangler.cattle.io/*` finalizers), APIServices, and `rancher.cattle.io`/`capi-*` webhooks — none flux-managed, so deleting the Rancher Kustomization does NOT remove them. Full teardown done 2026-06-01 by filtering cluster-scoped objects created in the install time-window and excluding native `k3s.cattle.io`/`helm.cattle.io` CRDs.
